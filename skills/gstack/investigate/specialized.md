# Specialized investigation

## Performance
Record the observed metric, workload, environment and target. Profile the relevant boundary: request timing, query plan, CPU, allocations, queue/pool pressure or browser performance. Identify the measured bottleneck, test one causal change and compare under matched conditions. A faster unrelated microbenchmark does not prove the user-facing problem is fixed.

## Environment differences
Compare runtime and locked dependency versions, deployed configuration, schema/migration state, services, permissions, network and intended feature flags. Inspect only relevant values; do not dump secrets or entire environments into logs. Test the suspected difference against the reproduction.

## Regressions
Inspect relevant history first. Use bisect only with a meaningful known-good revision and sufficiently cheap, reliable reproduction. Run it in an isolated checkout, preserve unrelated dirt and reset the bisect state afterward. A regression report can involve data/config as well as source changes.

## Intermittent failures
A flake is a test whose verdict depends on something other than the code it guards; no rerun, wider timeout, retry or skip until the cause is named and probed. Check out the base branch in a worktree and run the failing file alone at least ten times there and on the branch; record failed-over-runs for each. A failure that reproduces on the base is outside the change, one that appears only on the branch is inside it. Diff the two runs' logs at the first divergence and name the dependency (timing, file order, shared state, network, clock, a resource limit); "flaky" is a symptom, never a cause. Then build the smallest change that makes the test fail deterministically for that cause (inject the delay, pin the file order, freeze the clock, exhaust the resource) and show it failing before the fix and passing after; no probe, no cause. For a timing assertion, log the measured value and run at least twenty times on base and head under the same load, reporting min, median, p95, max and failures against the bound; a distribution that moved on the head is a regression, the same distribution on both is a test that depends on machine load. Fix the measurement, never the bound: assert on the outcome, an injected clock, a forced deadline or a poll with a deadline instead of a fixed sleep. A rerun is admissible only when the cause is known and outside the change, and it is diagnostic, never the green.

## Order-dependent failures
A polluter is an earlier test that leaks state the victim depends on: the victim passes alone and fails in the suite or in one shard. Take the files that ran before the victim in the failing run's order and confirm the victim passes alone and fails after them. Halve the earlier list, keep the half that still fails the victim and repeat until one file remains, logging the list at each step. Read the polluter for state that outlives it: an environment variable, the working directory, the process exit code, a module-level cache or singleton, a mock or spy left installed, a server or watcher left listening, a temp file under a shared path, a global timer. Fix the polluter where the state is created (teardown, a private temp directory, a private environment); a reset added to the victim's setup hides the leak for the next victim. If the polluter is on the base branch, the victim's failure is outside the change.

## Races
A race is two actors touching shared state with an ordering nobody enforces; make it deterministic before fixing it. Log a monotonic timestamp and actor id at every read and write of the shared state and keep the output as evidence. Inject an await or sleep at the suspected point in one actor, behind a test-only hook or environment variable, so the other actor runs in the window: the bug must now appear every time, and if it does not, the window is elsewhere. Drive several writers at once under that interleaving and assert the invariant (exactly one winner, all applied, the row or file intact, the lock released with its owner recorded), not the absence of an error; that test, with the interleaving still injected, becomes the regression test. The fix is an atomic primitive: create-exclusive, compare-and-swap, an update conditioned on the old value, or a lock with an owner token and a stale-owner rule. A check-then-act with a smaller window is not a fix. Rerun the concurrent test after the change and record both outputs.
